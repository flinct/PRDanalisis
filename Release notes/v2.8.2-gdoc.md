**Date:** 03-08-2026
**Server Environment:** production

## Highlights

This release ships **WhatsApp Group Mention** (mention group participants via the `@` trigger), the **interactive Agent Statistic Dashboard** (clickable cards, navigate-with-filter, drill-down modal), a **created-at column** on the broadcast template list, and an **inbound-message → outbound webhook relay** for partner verification (Salfok integration). It also lands a cluster of **agent-metrics / SLA correctness fixes** around conversation close — bulk-close attribution, TTC computed against the correct agent shift, non-credited participant cleanup — plus a fix restoring the **Ticket KPI card** in Analytics. Four items (WhatsApp API account-status handling, notification-service and Instagram-queue RabbitMQ stability fixes, and group-type detection) are **released and usable, currently in a monitoring phase**.

> Items marked **Closed / Tested** are fully live. Items in the **Released — Monitoring Phase** section are live and usable but still under observation.

## Bug Fixes

### Conversation / Agent Metrics

* **[#3522] Bulk Action Close — Agent Metrics Not Finalized** — *Tested*
Closing a conversation (single or bulk) failed to finalize agent metrics. Root cause: asymmetric write/read — metrics rows are created keyed on the **participant** but looked up on the **requester** at close time. Three call sites (`closeConversation:1704`, `junkConversation:3542`, `bulkJunkConversations:6175`) all sent `closingAgentId: userId` (the requester). Fixed the attribution to resolve the correct participant.

* **[#3565] SLA TTC Computed Against Closing User's Shift Instead of Handling Agent's** — *Tested*
SLA business-hours TTC was calculated against the **closing user's** shift (a supervisor/admin never assigned to the conversation) instead of the handling agent's, so `slaTtcSuccess` was evaluated against the wrong office hours and timezone. Unlike #3522 (which wrote nothing), this wrote a **wrong value**, quietly contaminating historical SLA data.

* **[#3588] Non-Credited Participants Stay in Active Agent-Metrics Set After Multi-Participant Close** — *Closed*
When a conversation with two or more participants was closed, only the credited agent's row was finalized — every other participant's row kept `agentTtcMs` unset, so a closed conversation counted forever as an active assignment for those agents. Split out of #3522. Fixed in `agent-conversation-metrics.service`.

### Analytics

* **[#3644] Ticket KPI Card Not Showing** — *Tested*
`GET /api/analytics/ticket/counts` returned HTTP 500 because the request was served by the legacy Redash path, and the Redash data source behind it is dead. Fixed by routing to the pre-aggregation path.

## Released — Monitoring Phase (Status `In testing`, usable by users)

> Released to production and usable, still under observation before final closure.

* **[#2208] WhatsApp API — Handle Account Channel Status Update** — *In testing*
Two defects in `apps/whatsapp-api`: account-status webhooks (`ACCOUNT_UPDATE`, `ACCOUNT_BANNED`, `ACCOUNT_REINSTATED`, etc.) are declared but never produced/consumed (no resolver registered); plus a second related channel-status defect.

* **[#3328] notification-service Crashes on RabbitMQ consumer_timeout (reminder-queue)** — *In testing*
Production incident 2026-08-20: notification-service crashed with `406 PRECONDITION_FAILED — delivery acknowledgement on channel 1 timed out` (1,800,000 ms). Root cause: `reminder-queue` runs `noAck: false` (`createRabbitMQDelayedQueueMicroservice`) and NestJS holds a delivery unacked past RabbitMQ's `consumer_timeout`, so the broker force-closes the channel and the process crashes.

* **[#3367] Instagram Token Refresh Queue Stuck — 540 Messages Unacked** — *In testing*
`instagram-token-refresh` queue sat at 540 unacked messages, never draining. Same `noAck: false` delayed-queue pattern (`main.utils.ts:283`, registered in `apps/instagram/src/main.ts:45`); long-lived Instagram tokens (60-day) reschedule via `x-delayed-message` exchange but deliveries pile up unacked.

* **[#3599] Conversation Group Type** — *In testing*
Lion Parcel case: scanning ~600 groups, most conversations created with `isGroup:false` instead of `true`; group name must sync on new groups instead of showing the raw `remoteJID`.
