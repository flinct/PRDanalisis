New Issues Introduced by v2.0 (Blocking for TRD)
NI-01: Direct-to-S3 multipart upload from analytics-service — presigned download path not guaranteed
Gap: Analytics-service currently has no AWS/S3 credentials or SDK. It uploads via mediaService.uploadMedia() gRPC call. v2.0 proposes direct multipart upload but:

apps/analytics-service/src has zero AWS_S3 / @aws-sdk/client-s3 references (grep count = 0)
apps/media-service/src/app/app.service.ts:51-57 initializes S3Client from media.accessKeyId, media.secretAccessKey, media.bucket, media.region (config factory libs/common/src/lib/config/configurations/media-config.ts:23-31)
Download: media-service generates presigned URL by HeadObject → generatePresignedUrl(key) where key = company/export_reports/[resourceKey/]mediaName (apps/media-service/src/app/app.service.ts:301-314)
Risk: If analytics-service uploads directly with a different key structure (or without resourceKey), media-service cannot find the object to generate the download URL. The PRD does not specify the exact key format analytics-service must use.
Suggested Rewrite (§12, §17, §18):

> "analytics-service will use @aws-sdk/client-s3 with the same media config namespace (AWS_S3_* env vars) to perform multipart upload. The S3 key MUST follow the existing pattern: {companyId}/export_reports/{mediaName} (where mediaName = the fileResult.name stored on the job document). This ensures the existing media-service.getMedia() presigned-URL path works without changes. Owner: Engineering. Rollback: revert to gRPC media hop for files < 20MB."

NI-02: Per-sheet 200,000 cap "supersedes 20K for this preset only" — shared code path bypass not explicit
Gap: The three domain export services enforce 20K before generation in their respective services (ticket-export.service.ts:187, conversation-export.service.ts:183, broadcast-export.service.ts:189). The SAP path in analytics-service does not call those services (it reads PRD-A collections directly and calls new people-service RPC), so it naturally bypasses the domain limits. However, the PRD must explicitly state:

1. The SAP generator code path does not reuse any shared utility that enforces the 20K cap (verify: no such shared utility exists — each domain service has its own constant and check).

2. The 20K constants remain unchanged and enforced for ticket/conversation/broadcast channels.

Suggested Rewrite (NFR-004, §12):

> "NFR-004: Per-sheet row cap = 200,000 for the SAP preset's code path in analytics-service. The three domain export paths (ticket/conversation/broadcast channels) retain their existing *_EXPORT_LIMIT = 20,000 constants and pre-generation checks. The SAP generator does not invoke domain export services and therefore does not pass through their limit guards. No shared utility enforces the 20K cap across channels."
