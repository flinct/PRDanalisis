# SatuInbox Mobile — Technical Reference (for Product Lead)

> **Purpose:** a self-contained picture of the mobile app for someone who does **not** have repo access.
> **Repo:** `satuinbox-mobile` (local remote `origin`, default branch `main`)
> **Product:** the field-facing companion to the SatuInbox web dashboard — agent inbox, field visits, and leads on a phone.
> **Backend:** the same NestJS API the web app uses (`v2-api.satuinbox.com`), REST under `/api` and Socket.IO on the same host.
>
> **State captured:** branch **`dev`** at `1921fb8`, app version **`1.0.4`** (iOS build `11`).
> Verified directly against the working tree on **2026-08-12**.
>
> ⚠️ **Read this first:** there are **no git tags in this repo** — no release history to point at, and no "production tag" equivalent to the web app's `prod-2.7.0.3`. What ships is whatever was last built through EAS. `feat/ticketing` (§15) is committed but **not merged into `dev`**.

## 4. Mobile Rules

- **Zustand owns everything stateful.** There is no React Query. Stores hold the data, the loading/refreshing/error flags, and the fetch actions themselves (`fetchTickets`, `refreshTickets`, `loadMoreTickets`). Screens call store actions through a feature hook.
- **Routes are re-exports.** Put logic in `src/features/`, not in `app/`.
- **Raw API shapes never reach components** — normalise in `mappers/`.
- **Tokens go through `src/utils/storage.ts`**, which is SecureStore on device and `localStorage` on web. Never touch SecureStore directly.
- **All API calls go through `src/services/api.ts`.** Bypassing it skips token injection, proactive refresh, and the network-vs-rejection error classification everything downstream depends on.
- **All socket work goes through `socketService`** — `.on()` for listeners and `.onConnect()` for room joins, never `socket.on()` on a raw instance (§9 explains why).
- **No i18n.** All copy is hardcoded English in the components; there is no `next-intl` equivalent and no lint rule guarding it. Note the web app is `id`-default — the mobile app is English-only.
- **Styling is `StyleSheet.create` + design-token constants** (`COLORS`, `SPACING`, `TYPOGRAPHY`, `BORDER_RADIUS` from `src/const/`). No Tailwind, no styled-components. `COLORS` is a 50–900 ramp per hue, brand primary `#007AFF`.

### Feature stores

| Store | Feature | Purpose |
| --- | --- | --- |
| `useAuthStore` | auth | Tokens, user, role, onboarding status, login/logout/refresh/checkAuth. **Persisted.** |
| `useChatStore` | chat | Conversation list, filters, inbox + filter counts, typing-by-conversation |
| `useChatDetailStore` | chat | Open conversation: messages, drafts, attachments, utilities, downloads |
| 15 stores under `visit/store/` | visit | `visitStore` `visitListStore` `visitDetailStore` `visitSubmitStore` `leadStore` `leadListStore` `leadDetailStore` `leadMutationStore` `leadCompanyStore` `contactStore` `contactLeadStore` `channelStore` + two list-store factories (`createVisitListStore`, `createLeadListStore`) + a `dummy` fixture file |

The visit feature's 15 stores are the clearest place the store-per-concern approach has sprawled; two of them are factories and one is dummy data.

### Persistence

Only `useAuthStore` is persisted, via Zustand `persist` + AsyncStorage under key `auth-storage`, partialised to `token` / `refreshToken` / `user` / `role` / `isAuthenticated`. The tokens are *also* written to SecureStore under `auth_token` / `refresh_token` — SecureStore is the copy the axios interceptor reads.

### Chat detail caching

`useChatDetailStore` keeps **one active conversation** (`conversationId`, `messages`) plus an **LRU cache of 10 conversation snapshots**, so reopening a recent chat renders on the first frame instead of showing a spinner. Insertion-ordered object keys are the LRU mechanism; the cache object is always rebuilt, never mutated, so subscribers see a real change. Because there is still only one *active* slot, two chat screens on the stack cannot both be live — the screen hydrates from cache on focus.

## 7. API Integration

### Axios flow (`src/services/api.ts`)

- Single `apiClient`, base URL from `app.config.js` `extra.apiUrl`, **30s timeout**, `User-Agent` built from app name + version + platform + device model.
- **Request interceptor:** reads the token from SecureStore and injects `Authorization: Bearer …`. It decodes the JWT `exp` and **proactively refreshes 60 seconds before expiry** rather than waiting for a 401. Auth endpoints are exempt.
- **Response interceptor:** on `401` (non-auth endpoint, not already retried), refreshes and replays the original request. Concurrent 401s share one refresh via an `isRefreshing` flag plus a `failedQueue`.
- **Error shape:** `AxiosError` is collapsed into a plain `Error` carrying `status`, `isNetworkError`, and `code`. `isNetworkError` (i.e. `!error.response`) is the field that distinguishes "the server rejected us" from "this device has no signal" — the whole offline-resilience story in §8 depends on it, and there is an exported `isNetworkError(err)` helper.
- `__devExpireToken()` is a `__DEV__`-only helper that plants a bad token so the refresh path can be exercised on demand.

There is **no response envelope unwrapping** — services read `response.data` directly. The web app's `ApiResponse<T>` wrapper has no counterpart here.

## 8. Authentication & RBAC

1. `POST /auth/login` with `{ identifier, password }` → `{ accessToken, refreshToken, user, role, onboardingStatus, sessionId }`.
2. Tokens written to SecureStore; store state set; `socketService.connect(accessToken)`.
3. **Cold start (`checkAuth`)** always refreshes: no stored refresh token → unauthenticated; otherwise refresh, decode the role out of the new access token, reconnect the socket.
4. Role comes from the **JWT payload** (`role.permission[]`) via `mapTokenRoleToRole`, not from a separate endpoint — so a permission change only lands after a token refresh.

### Refresh hardening

This is the most carefully-worked part of the codebase, and the reasoning is worth carrying:

- **One in-flight refresh, shared.** The backend *rotates* the refresh token, so two overlapping refreshes race: the first succeeds and invalidates the token, the second fails and used to trigger a hard logout. Every caller — axios 401, app foreground, socket recovery, `checkAuth` — awaits the same promise.
- **Only the server saying no logs you out.** `REFRESH_REJECTED_STATUSES = {400, 401, 403, 422}`. A network error, a timeout, a 500, or a missing status leaves the session intact and lets the caller retry. Previously three socket errors in a tunnel wiped both tokens.
- **Offline cold start keeps you signed in.** If the launch refresh can't reach the server but credentials are stored, the session is restored from the stored access token (role decoded locally, tolerating a malformed token) and the app opens on cached data.
- **Foreground refresh.** On `background → active` (deliberately *not* `inactive`, which iOS emits for Control Center, banners, and biometric prompts) the app calls `socketService.resume()` first — independently of the refresh, because sockets back off up to 30s and a live screen with a dead socket reads as "chat is broken" — then refreshes the token.

### RBAC

`usePermission()` exposes `can(permission)` and `canRead(resource)`. `*` is all-access. `canRead` accepts any of `read` / `read_own` / `read_team`. The enums (`ResourceTypeEnum`, `PermissionActionEnum`) mirror the backend's and are far broader than the mobile app uses — mobile reads `conversation`, `lead`, `visit`, `client_contact`, `ticket`. There is no privacy-masking equivalent to the web app's `usePrivacyMasking`.

### Account lifecycle

Logout tears down the socket, revokes the push token **while the bearer token is still valid**, clears Firebase user identity, then deletes both stored tokens. `deleteAccount` calls `/auth/deactivate` then logs out; the entry point is **iOS-only** in the profile screen (an App Store review requirement).

## 9. Realtime (Socket.IO)

Same host as the API. One `Socket` per namespace, keyed by sub-path; the chat feature uses **`conversations`**. Handshake auth is `{ token, type: 'bearer' }`.

Connection options: `autoConnect: false`, `reconnectionAttempts: Infinity`, delay 1s → **max 30s**, randomisation 0.5, transports `['websocket', 'polling']` with **`tryAllTransports: true`** — without that flag socket.io-client 4.8 never walks to the fallback, so a network blocking the WebSocket upgrade (proxy, VPN, some carriers) retried websocket forever.

`socketService` is a hand-written manager, and most of it exists to survive failure modes seen in the field:

| Behaviour | Why |
| --- | --- |
| `on()` registers against the **namespace**, not the instance | Listeners are replayed onto a rebuilt socket, so callers never learn the instance was swapped |
| `onConnect()` hooks run on **every** connect | Room membership is keyed to the socket id and does not survive a reconnect — join must be re-emitted, not done once on mount |
| Auth refresh after **3** consecutive `connect_error`s, 30s cooldown | A wedged reconnect loop usually means an expired JWT |
| …but **skipped entirely for `TransportError`** | The connection never presented a credential — the device is offline. Asking for a token can't help, and the refresh call fails too, which used to cascade into a hard logout |
| Socket **rebuilt from scratch after 8** failures (60s cooldown), with `forceNew` | Observed in the wild: every attempt fails with a contentless `websocket error` while plain HTTP from the same app works, and only a fresh socket recovers — this is the automated version of "log out and back in". `forceNew` is essential because `io()` caches one `Manager` per origin+path and would otherwise reuse the wedged engine |
| Manager listeners tracked with an explicit teardown | They live on `socket.io`, which `removeAllListeners()` does not touch — leaking them gives duplicate status updates after every rebuild |
| Reconnect logging throttled (first 3, then every 10th) | A dead network otherwise buries every other dev log |
| `resume()` cancels backoff on foreground | See §8 |

### Chat events (`src/features/chat/const/events.ts`)

The backend does not use one consistent naming pattern — both `notification.<action>.<resource>` and `notification.<resource>.<action>` appear on the wire, so the constants file marks each event **confirmed** or **guessed**, and a `__DEV__` `onAny` logger prints every inbound event so guesses can be corrected against reality.

| Direction | Events |
| --- | --- |
| Inbound (confirmed) | `notification.new.message` · `notification.message.status` · `ticket.created` · `typing.indicator` · `conversation.closed` |
| Inbound (unconfirmed) | `notification.message.read` · `notification.new.conversation` · `notification.conversation.updated` · `notification.conversation.deleted` · `notification.inbox.counts` |
| Outbound | `conversation.join` · `conversation.leave` · `conversation.read` · `typing.start` · `typing.stop` · `socket.outbound.message` |

Typing is asymmetric: clients emit `typing.start`/`typing.stop`, the server broadcasts a single `typing.indicator` with `isTyping`.

### Two subscriber hooks

- **`useChatListSocket`** — the always-on one. Bumps rows on new messages, upserts/removes conversations, flips `status: "close"` on `conversation.closed` (in both the list and the open detail snapshot), flips `isTicket` on `ticket.created`, tracks typing per `conversationId:userId` with a **4s safety timeout** in case the stop event is dropped, **debounces a REST counts refresh by 500ms** so a burst of messages doesn't hammer the count endpoints, and fires the local notification for inbound messages.
- **`useChatDetailSocket`** — joins/leaves the conversation room (join via `onConnect`, so reconnects re-join), applies message/status/read events to the open timeline, marks inbound messages read immediately, and returns `notifyTyping()` for the composer.

## 10. Push Notifications & Telemetry

### Push — Expo, deliberately not Firebase Messaging

Push goes through **Expo's push service** via `expo-notifications`; the app sends `ExponentPushToken[...]` values, not FCM registration tokens. `@react-native-firebase/messaging` **must never be installed** — it would claim the `com.google.firebase.MESSAGING_EVENT` intent filter that `expo-notifications` owns and Android push would silently break. Expo holds the FCM V1 service account key and the APNs key and talks to Google/Apple on our behalf.

Behaviour worth knowing:

- **The notification handler is the only gate remote pushes pass.** Foregrounded and already viewing that conversation → suppressed entirely (not even added to the tray, since the socket already rendered the message). Foregrounded on a different conversation → shown as a heads-up. Backgrounded → always shown.
- "Which conversation is on screen" is derived from the **router pathname**, not from the chat screen's own focus, so it clears correctly however the user leaves (back gesture, deep link, tab switch). `/chat/:id/info` deliberately does not count as viewing the chat.
- **Taps use `router.push`, not `navigate`.** Both chat screens resolve to the single `/chat/[id]` route name, and `navigate` reuses the existing screen and swaps its params — so tapping a notification for chat A while inside chat B overwrote B and back skipped past it.
- The tap listener is held at module scope and replaced rather than added, because `addNotificationResponseReceivedListener` registers an *additional* listener per call; without that, each Fast Refresh stacked another and one tap navigated once per stale listener.
- `getPushToken()` returns `null` without throwing on simulators, on denied permission, and when the EAS `projectId` is missing — callers treat that as "push unavailable", never an error. In `__DEV__` the token is printed bare on its own line so it can be triple-clicked into `expo.dev/notifications`.

> ⚠️ **Backend gap:** `POST /device/push-token` and its revoke counterpart **are not implemented on the API**. The client posts to assumed paths, and `registerPushToken()` currently logs a Crashlytics non-fatal and no-ops. Delivery is still testable through `expo.dev/notifications`, but **targeted push does not work end-to-end yet.** The contract the backend needs to implement is fully written up in `firebase/BACKEND_PUSH_SPEC.md` — including the concurrent-sessions-with-global-logout token model (many tokens per user, logout deletes all of them) and the note that only the status code matters, since the client ignores the response body.

### Telemetry — Firebase Analytics + Crashlytics

Modular RNFB API (v22+). Every wrapper is individually guarded by a `guard()` helper that swallows both throws and promise rejections, so an app running without the native module (Expo Go, or a binary predating the Firebase install) degrades to a no-op instead of crashing.

- `identifyUser` sets the user id plus `company_id` / `organization_id` on both SDKs. **Email, phone, username and full name are deliberately not sent** — opaque IDs only.
- Screen views come from `useScreenTracking`, not Firebase's automatic reporting: with expo-router the whole app is one Activity/UIViewController, so the SDK only ever sees one screen. Dynamic segments are collapsed (`/chat/:id`) so Analytics doesn't get one row per conversation. `logScreenView()` is avoided because RNFB marks it deprecated and warns on every call; the hook emits the equivalent `screen_view` event directly.
- Both route-watching hooks live in **`<RouteTracker />`**, a component that renders `null`. They call `usePathname()`, which re-renders the caller on every navigation — calling them in the root layout re-rendered `<Stack>` and remounted the active screen, which in chat surfaced as a mount/unmount loop that refetched messages forever and left the screen permanently loading.

Payload assembly is isolated in `buildCheckInPlayload.ts` [sic]; the flow is driven by `useCheckInAction` / `useCheckInCamera` / `useCheckInLocation` / `useCheckInSubmit` and `visitSubmitStore`.

### Two components worth knowing about

**`components/common/SafeAreaView.tsx` — a local drop-in shim.** The library's `SafeAreaView` wraps a native view that applies insets during *native* layout, i.e. after the first JS render, so content painted flush to the screen edge for a frame and then jumped — plainly visible during a stack push. The shim reads `useSafeAreaInsets()` and applies them as ordinary padding in the same render. It correctly reproduces the library's additive edge mode, honouring RN's specific > axis > shorthand padding precedence. **It depends on the root `SafeAreaProvider` being given `initialWindowMetrics`** — without that the hook returns zeros on first render and the flash returns. Screens should import `SafeAreaView` from here, never from `react-native-safe-area-context`.

**`MessageBubble` is memoised** as part of a scroll-performance fix — every bubble used to re-render on each scroll tick. A fresh inline arrow function passed as a prop at the call site silently defeats the memo and reintroduces the jank.

### Root provider stack (`app/_layout.tsx`)

`GestureHandlerRootView` → `SafeAreaProvider(initialWindowMetrics)` → `KeyboardProvider` → `GlobalBottomSheetProvider` → `MenuProvider` → `StatusBar` + `RouteTracker` + `Stack`, with `Toast` mounted outside the menu provider.

`KeyboardProvider` publishes keyboard position per frame as shared values. Only `InputChatArea` consumes it today, and the Android soft-input mode it needs is set and restored by the consuming hook rather than globally. The chat layout is `max(keyboard, panel)` — jumps in the attachment-panel swap are fixed there, never by reordering keyboard events.

## 13. Native Configuration & Build

`app.config.js` is the single source of truth, and **the plugin order in it matters**:

1. **`expo-build-properties` must come first.** `firebase-ios-sdk` requires `use_frameworks!`, and from Expo 54 on every RNFB pod must *also* be listed in `forceStaticLinking` (`RNFBApp`, `RNFBAnalytics`, `RNFBCrashlytics`) to coexist with React Native's prebuilt-core system. Without it the iOS build fails on non-modular-header errors inside `RNFBApp`.
2. `@react-native-firebase/app` — injects `FirebaseApp.configure()` on iOS and the google-services Gradle plugin on Android.
3. `@react-native-firebase/crashlytics` — Android symbol upload.
4. **No `@react-native-firebase/analytics` plugin entry**, on purpose: it only sets optional iOS Podfile flags and is a no-op without props. Analytics works without it.
5. Then `expo-router`, `expo-secure-store`, `expo-font`, `react-native-vision-camera`, `expo-image-picker`, `@react-native-community/datetimepicker`, `expo-notifications`.

**`android/` and `ios/` are gitignored** — the native projects are generated by `npx expo prebuild`. Anyone cloning the repo must prebuild before a local device run.

### Firebase files

`firebase/dev/` and `firebase/prod/` each hold a `google-services.json` and a `GoogleService-Info.plist`. All four are required; `expo prebuild` **throws** (not warns) if the file for the current `APP_ENV` is missing. The `package_name` / `BUNDLE_ID` inside each must match the flavour exactly or the native build succeeds and FCM silently never issues a push token. These files contain only public identifiers and are **tracked on purpose**. What is secret and gitignored: the **FCM V1 service account key**, uploaded to EAS via `eas credentials`.

## 18. Standing Constraints (read before debugging)

Things that have already cost time on this project, in rough order of how often they resurface:

1. **A silent image/file load failure is probably the S3 presigned URL expiring.** Attachment URLs are valid for 15 minutes and there is no refresh path. Check this before anything else.
2. **Socket wedged?** Reconnects and token refreshes do not clear it — only rebuilding the instance does, which `socketService` now automates after 8 failures. Always register listeners via `socketService.on()` and room joins via `socketService.onConnect()`, or they will not survive the rebuild.
3. **A socket transport error is never an expired JWT.** The `/conversations` namespace has no connect-time auth — any token connects — so a `TransportError` means the network, not the credential.
4. **Don't fix keyboard jumps by reordering keyboard events.** The chat layout is `max(keyboard, panel)` via `keyboard-controller`.
5. **Don't restore the tuned chat route animation on iOS.** `chat/[id]` intentionally uses `slide_from_right` there.
6. **Don't add a `transition`-keyed fade over cached content.** `Animated.Value(0)` plus a transition-keyed fade renders synchronously-available cached content invisible.
7. **Import `SafeAreaView` from `src/components/common/`, not the library** (§12).
8. **Don't bump `@react-native-firebase/*` past v24.x**, and **never install `@react-native-firebase/messaging`** (§10, §13).
9. **A fresh inline arrow prop on `MessageBubble` silently reintroduces the scroll jank** (§12).
10. **Build iOS device binaries on EAS**, not locally — `aps-environment` needs an explicit App ID.
